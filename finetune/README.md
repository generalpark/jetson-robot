# 자연어 주행 명령 → 제어 명령 변환 (LoRA 파인튜닝)

Jetson Orin Nano 8GB에서 소형 언어모델을 파인튜닝해, 사람이 말하듯 준 주행 명령을
로봇이 그대로 받아쓸 수 있는 제어 명령(JSON)으로 바꾼다.

```
"5초 동안 앞으로 천천히 가면서 왼쪽으로 틀어"
   ↓
{"linear": 0.15, "angular": 0.24, "duration": 5.0}
```

출력 형식은 ROS2 `geometry_msgs/Twist`의 선속도·각속도를 그대로 따른다.

## 왜 파인튜닝까지 했나

먼저 학습 없이 프롬프트만으로 되는지 확인했다. 같은 시스템 프롬프트를 쓰고,
예시를 주지 않은 경우와 3개 준 경우를 각각 측정했다.

예시를 주자 **형식은 완전히 교정됐지만(스키마 62.7% → 100%) 값 정확도는 거의 그대로였다**
(완전일치 1.3% → 2.0%). 형식은 프롬프트로 잡히지만, "천천히"가 0.15 m/s라는
도메인 고유의 대응은 프롬프트로 전달되지 않는다고 보고 학습으로 넘어갔다.

## 결과

| | JSON 파싱 | 스키마 일치 | 방향(부호) | 값 완전일치 |
|---|---:|---:|---:|---:|
| 형식 지시만 (zero-shot) | 100.0% | 62.7% | 14.0% | 1.3% |
| 예시 3개 (few-shot) | 100.0% | 100.0% | 42.0% | 2.0% |
| **LoRA 학습 후** | **100.0%** | **100.0%** | **86.0%** | **74.7%** |

측정은 테스트 150건, 그리디 디코딩 기준이다.

## 검증 손실이 말해주지 않은 것

학습이 끝났을 때 검증 손실은 0.000027이었다. 숫자만 보면 다 맞히는 모델이다.
그런데 같은 모델의 테스트 완전일치는 74.7%였다.

검증셋이 학습과 같은 어휘로 만들어졌기 때문이다. 테스트셋을 **학습에 나온 표현 75건**과
**학습에 없던 표현 75건**으로 절반씩 나눠 다시 재보니 차이가 분명했다.

| LoRA | 방향(부호) | 값 완전일치 |
|---|---:|---:|
| 학습에 나온 표현 (75건) | 100.0% | **100.0%** |
| 학습에 없던 표현 (75건) | 72.0% | **49.3%** |

**틀린 38건은 전부 학습에 없던 표현이었다.** 학습 어휘 안에서는 한 건도 틀리지 않았다.

### 어떻게 틀렸나

| 입력 | 정답 | 생성 | 무슨 일이 났나 |
|---|---|---|---|
| 앞으로 **살살** 가면서 좌측으로 틀어 | linear 0.15 | 0.3 | 모르는 속도어 → 기본값으로 대체 |
| **뒤쪽으로** 가 | linear −0.3 | angular −0.72 | 모르는 방향어 → 다른 항목으로 흘림 |
| 오른쪽으로 **전속력으로** 돌아 | angular −1.2 | −0.72 | 모르는 강도어 → 중간값 |

로봇에서는 두 번째가 가장 위험하다. 후진 명령이 회전 명령이 되면 값이 조금
어긋나는 것과는 다른 종류의 사고가 된다. 속도를 덜 내는 것은 느려질 뿐이지만,
명령의 종류가 바뀌면 의도하지 않은 방향으로 움직인다.

### 대조군을 다시 만든 이유

처음 만든 테스트셋은 150건 중 146건에 새 어휘가 섞여 있었다. 문장이 방향·속도·
어미 등 여러 자리를 쓰다 보니, 한 자리만 새 어휘여도 전체가 "새 표현"으로 분류됐다.
대조군이 4건뿐이어서 비교가 성립하지 않았고, 두 그룹을 75건씩 맞춰 다시 생성했다.

## 지표를 이렇게 나눈 이유

한 개의 정확도만 보면 무엇이 고쳐졌는지 알 수 없다. 실패가 어느 단계에서
나는지 구분하려고 네 단계로 나눴다.

| 지표 | 보는 것 |
|---|---|
| JSON 파싱 | 출력이 JSON이기는 한가 |
| 스키마 일치 | 필요한 키 3개가 모두 있고 숫자인가 |
| 방향(부호) | 앞뒤·좌우를 반대로 보내지 않는가 |
| 값 완전일치 | 속도·시간까지 맞는가 (허용 오차 0.02) |

로봇에서는 **부호가 틀리는 것이 값이 조금 틀리는 것보다 위험하다.**
속도가 0.3이어야 하는데 0.25인 것은 느리게 갈 뿐이지만, 부호가 뒤집히면
반대로 간다. 그래서 부호를 따로 뒀다.

## 어휘를 넓히면 나아지는가 (실험)

일반화가 안 되는 원인이 학습 어휘가 좁아서인지 확인했다.
**데이터 양은 800건으로 고정하고 어휘만 넓혔다**(고유 토큰 33 → 47).
양을 함께 늘리면 무엇이 효과를 냈는지 분리할 수 없다. 테스트셋도 그대로 뒀다.

| 학습에 없던 표현 75건 | 방향(부호) | 값 완전일치 |
|---|---:|---:|
| 기본 어휘 | 72.0% | 49.3% |
| 어휘 확장 | **78.7%** | **49.3%** |

방향은 6.7%p 올랐고 값 정확도는 변하지 않았다. 고쳐진 7건은 전부 방향 오류였고,
그 중 다수는 방향만 바로잡힌 채 값은 여전히 틀렸다.

| 입력 | 기본 | 확장 | 정답 |
|---|---|---|---|
| 우측으로 천천히 돌아 | angular +0.36 | **−0.36** | −0.36 |
| 앞쪽으로 살살 가봐 | angular 0.36 | linear **0.3** | linear 0.15 |

값이 틀린 38건에 들어 있던 새 단어는 `살살`(15), `뒤쪽으로`(14), `전속력으로`(11) 순이었다.
속도어가 남았다.

| 종류 | 어휘 확장 효과 | 이유 |
|---|---|---|
| 방향 (우측으로, 꺾어) | 개선 | `우`·`왼` 등 형태 단서가 있고 문장 내 위치로 유추된다 |
| 속도 등급 (살살, 전속력으로) | 없음 | 형태로 유추할 수 없고 단어의 뜻을 알아야 값이 정해진다 |

**여러 개 중 하나를 고르는 문제는 데이터 다양성으로 개선되지만, 단어를 수치로
옮기는 문제는 개선되지 않았다.** 후자는 데이터를 더 모으는 대신 사전 정규화나,
모르는 단어를 만났을 때 지어내지 않고 되묻는 장치가 맞다고 본다. 로봇에서는
틀린 값으로 움직이는 것보다 멈추고 확인하는 편이 낫다.

재현:

```bash
./run_rich.sh
```

## 데이터

합성 데이터 1,050건(학습 800 / 검증 100 / 테스트 150)을 규칙으로 생성했다.

테스트셋에는 **학습에 한 번도 나오지 않은 표현**을 섞었다(`살살`, `전속력으로`,
`좌측으로`, `앞쪽으로` 등). 학습 어휘로만 평가하면 외운 것인지 규칙을 익힌 것인지
구분할 수 없기 때문이다.

## 8GB에서 돌리기

전체 파라미터 학습은 메모리에 들어가지 않아 LoRA로 어댑터만 학습했다.

- 학습 대상 **8,798,208 / 502,830,976 = 1.75%**
- fp16, gradient checkpointing, batch 4 × 누적 4
- 손실은 정답 JSON 구간에만 건다. 프롬프트까지 학습하면 모델이 질문을 따라 쓴다

## 실행

```bash
python3 gen_data.py --out .          # 데이터 생성
./run_eval.sh zeroshot fewshot       # 학습 전 기준선
./run_train.sh                       # LoRA 학습
./run_eval.sh lora                   # 학습 후 측정
```

## 구성

| 파일 | 내용 |
|---|---|
| `gen_data.py` | 데이터 생성. 학습/테스트 어휘 분리 |
| `train_lora.py` | LoRA 학습. 프롬프트 구간 손실 제외 |
| `evaluate.py` | 4단계 지표 측정. zero-shot/few-shot/LoRA 공통 |
| `analyze.py` | 아는 표현 / 모르는 표현을 나눠 비교 |
| `run_eval.sh`, `run_train.sh` | 컨테이너 실행 |
| `run_rich.sh` | 어휘 확장 실험 (생성 → 학습 → 평가) |
| `offtopic.py` | 주행이 아닌 문장 목록 (학습용 191 / 평가용 60, 문장 단위로 분리) |
| `run_reject.sh`, `report_reject.py` | 거부 학습 실험과 전후 비교표 |
| `run_seeds.sh`, `report_seeds.py` | 시드 반복 학습·평가와 평균 ± 표준편차 |
| `run_logprobs.sh`, `analyze_confidence.py` | 토큰 확률 수집과 확신도 기반 되묻기 분석 |
| `run_1p5b.sh` | 1.5B 비교 실험 (8GB에서는 메모리 부족으로 중단, 큰 GPU용) |


## 데이터 양 스윕 (2026-09-30)

같은 설정에서 학습 데이터 양만 바꾸고 같은 테스트셋 150건으로 쟀다.

| 학습 데이터 | 값 완전일치 | 방향(부호) | 두 배로 늘릴 때 |
|---|---|---|---|
| 100개 | 41.3% | 71.3% | — |
| 200개 | 65.3% | 79.3% | +24.0%p |
| 400개 | 71.3% | 86.7% | +6.0%p |
| 800개 | 74.7% | 86.0% | +3.4%p |

두 배로 늘릴 때마다 얻는 폭이 줄고, 방향 정확도는 400개에서 포화한다. 틀린 답이 전부 학습에 없던
어휘에서 나왔던 것과 같은 결론이다. 같은 어휘로 양을 늘리는 것보다 **어휘 다양성**이 다음 개선 수단이다.

## 주행이 아닌 문장 거부 (2026-10-01)

실제 주행 경로에 붙여 보니 "오늘 날씨 어때"에도 좌회전 명령이 나왔다. 학습 데이터가 전부
주행 명령이라 모델이 모든 입력을 주행으로 읽는다. 주행이 아닌 문장 60개로 재보니 이랬다.

| 기존 모델 | 건수 | 움직이는 명령을 낸 비율 |
|---|---:|---:|
| 잡담 · 질문 · 다른 기기 명령 ("세탁기 돌려줘") | 35 | 57.1% |
| 주행 어휘가 든 비주행 문장 ("뒤로 가기 버튼 눌러줘", "10초 동안 숨 참아봐") | 25 | **100%** |

**방법** — 주행 데이터 800건과 테스트셋 150건은 한 글자도 바꾸지 않고, 정답이 `{"reject": true}`인
문장 191개만 더해 다시 학습했다(`offtopic.py`). 거부 효과만 따로 재기 위해서다.

- 평가용 60개는 학습 문장과 겹치지 않는다. 화면 버튼, 방향이 붙은 기기 명령("오른쪽 스피커만 켜줘")처럼
  **학습에 없는 유형**도 넣었다
- 정지 단어("멈춰", "그만" 등)가 든 문장은 거부 데이터에 넣지 않았다. 헷갈리는 문장이면 거부보다
  멈추는 편이 안전하므로, 정지 단어와 거부가 함께 학습되지 않게 했다

**결과**

| | 주행 완전일치 | 부호 | 잘못 거부 | 잡담 거부 | 잡담인데 움직임 | 헷갈림 거부 | 헷갈림인데 움직임 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 기존 모델 | 74.7% | 86.0% | 0% | 0% | 57.1% | 0% | 100% |
| 거부 학습 | 71.3% | 86.7% | 0.7% | **100%** | **0%** | **100%** | **0%** |
| 거부 학습 Q4_K_M | 71.3% | 84.0% | 1.3% | 100% | 0% | 100% | 0% |
| **+ 정지어 규칙 (배포)** | 72.0% | 84.7% | 0.7% | 100% | 0% | 100% | 0% |

- **주행이 아닌 문장 60건을 전부 거부했다.** 학습에 없던 유형도 포함이다. 다만 60건은 작은 표본이다
- **학습 어휘 75건은 전후 모두 100%다.** 완전일치가 3.4%p 준 것은 전부 학습에 없던 어휘 구간에서
  나왔다(9건이 바뀌어 7건 잃고 2건 얻음). → **시드 반복으로 다시 재 보니 편차였다.** 아래 "시드 반복" 참고
- 잘못 거부한 것: `세워`(학습에 없던 정지어), Q4에서 `앞쪽으로 살살 가봐`(세 단어 모두 처음 보는 어휘).
  후자는 앞에서 말한 "모르는 말이면 지어내지 말고 멈춘다"에 가까운 동작이다. **전자는 정지 명령을
  거부한 것이라 위험하다.** 그래서 정지는 모델에 맡기지 않는다. `infer.py`가 정지어(`멈춰`, `세워`, `중지` 등)를
  보면 모델을 부르지 않고 바로 정지 명령을 낸다. 테스트 150건에서 정지가 아닌 명령에 걸린 것은 0건이었고,
  "계획을 세워"처럼 엉뚱하게 걸려도 결과는 정지라 안전하다. 틀린 정지는 불편하고, 틀린 주행은 위험하다
- 거부는 응답도 빠르다. 짧은 JSON이라 요청당 약 170ms(주행 명령은 약 400ms)

재현:

```bash
./run_reject.sh     # 데이터 → 기준선 → 학습 → 평가 → GGUF 변환 → GGUF 평가 → 비교표
```

## 시드 반복 — 한 번 학습한 비교는 믿을 수 없었다 (2026-10-01)

위의 "완전일치 −3.4%p"는 각각 한 번씩 학습한 결과를 비교한 것이다. 같은 설정을 시드만 바꿔
3번씩 다시 학습했다(`run_seeds.sh`, `train_lora.py --seed`). 테스트셋은 그대로다.

| 시드 3회 평균 ± 표준편차 | 완전일치 | 학습 어휘 | 처음 보는 어휘 | 부호 | 비주행 거부 | 비주행인데 움직임 |
|---|---:|---:|---:|---:|---:|---:|
| 기존 | 72.0 ± 2.9 | 100 | 44.0 ± 5.8 | 84.4 ± 4.7 | 0 | 65.6 ± 17.3 |
| 거부 학습 | **77.8 ± 2.3** | 100 | **55.6 ± 4.7** | **91.8 ± 1.9** | 100 | **0** |

시드별 완전일치: 기존 70.0 / 70.7 / 75.3, 거부 학습 78.0 / 80.0 / 75.3. 처음 학습한 것은 기존 74.7, 거부 학습 71.3이었다.

- **−3.4%p는 거부 학습 탓이 아니었다.** 같은 설정이어도 학습마다 70~80% 사이에서 흔들리고, 처음 비교는
  운 좋은 기존 모델(74.7)과 운 나쁜 거부 모델(71.3)을 맞붙인 셈이었다
- 시드 3회 평균은 거부 학습 쪽이 높다. 다만 처음 실행까지 4개씩 넣으면 차이(약 3.5%p)가 편차 안이라,
  말할 수 있는 것은 **"거부 학습은 주행 정확도를 잃지 않는다"**까지다. 부호는 4개씩 넣어도 거부 학습 쪽이
  약 6%p 높다(84.8 vs 90.5)
- 학습 어휘는 모든 시드에서 100%다. 흔들리는 것은 처음 보는 어휘 구간뿐이다
- 배포 중인 거부 모델은 4개 중 점수가 가장 낮은 것이다. 그래도 바꾸지 않았다. 테스트 점수로 시드를 고르면
  테스트셋에 맞춰 고른 것이 되고, 그 점수는 더 이상 처음 보는 데이터의 성능이 아니다
- 교훈: 차이가 편차보다 작으면 한 번의 비교로 결론 내지 않는다. 이 프로젝트에서 앞서 낸 단일 비교들
  (어휘 확장, 데이터 양 스윕)도 같은 한계를 가진다

## 확신도로 되묻기 (2026-10-01)

틀린 답이 전부 처음 보는 어휘에서 나왔으니, 모델이 그 값을 고를 때 확률이 낮았다면 기준 아래에서는
움직이지 않고 되물으면 된다. **재학습 없이** 되는지 봤다(`run_logprobs.sh`, `analyze_confidence.py`).

- 확신도 = 출력한 숫자 토큰 확률의 최솟값. 결과를 보기 전에 이것을 주 지표로 정했다
- 기준은 테스트가 아니라 검증셋에서 정했다: "검증셋 정답의 99%(또는 95%)는 통과시키는 값"

배포 모델(거부 학습 Q4_K_M), 주행 테스트 150건:

| 되묻는 기준 | 되물음 (학습 어휘) | 잘못 움직임 | 부호 틀린 움직임 | 되물은 오답 | 되물은 정답 |
|---|---:|---:|---:|---:|---:|
| 없음 | 0 | 41 | 22 | — | — |
| 검증 정답 99% 통과 (τ=0.861) | 15 (2) | 34 | 18 | 7 | 8 |
| 검증 정답 95% 통과 (τ=0.991) | 28 (4) | 23 | **11** | 18 | 10 |

- 엄격한 기준이면 **부호가 틀린 움직임이 절반**이 되지만, 명령 5개 중 1개를 되묻는다
- **모델은 확신을 갖고 틀린다.** 오답의 확신도 중앙값이 0.995다. 처음 보는 속도어를 기본값으로 바꿀 때
  망설이지 않는다. 처음 보는 어휘 구간에서 정답·오답을 가르는 힘(AUROC)은 0.68에 그쳤다.
  모르는 것을 모른다는 신호가 약하다
- 거부 학습 전 모델은 AUROC 0.89로 더 잘 갈랐다. 다만 모델 한 쌍의 비교라 위의 교훈대로 판단을 보류한다
- 확률을 같이 받으면 요청당 0.1~0.2초가 더 든다
- 결론: 보조 수단으로는 쓸 만하지만 되묻는 비용이 커서 배포 기본값에는 넣지 않았다

### 디코딩 설정이 숨어 있었다

llama-server가 확률 0.63인 토큰 대신 0.37인 토큰을 고른 것을 보고 찾았다. Qwen2.5의 `generation_config.json`에
`repetition_penalty: 1.1`이 들어 있고, **transformers는 `do_sample=False`여도 이것을 적용하고, llama-server는
GGUF 메타데이터에서 같은 값을 기본값으로 가져온다.** 앞의 모든 수치는 이 조건에서 나왔다(양쪽이 같아 비교는 유효).
숫자 JSON에서는 앞에 나온 "0"을 깎아 값이 바뀔 수 있다. 끄고(1.0) 시드 3회로 재니 기존 70.7 ± 2.7,
거부 학습 77.6 ± 3.1로 **켠 경우와 편차 안**이었다. 그대로 둔다. `evaluate.py --repetition-penalty`,
`eval_gguf.py --repeat-penalty`로 바꿔 잴 수 있다.

## 모델 크기 1.5B — 이 보드에서는 학습하지 못했다 (2026-10-01)

처음 보는 속도어는 데이터 다양화로도, 확신도로도 안 잡혔다. 남은 가설은 "0.5B가 단어 뜻을 모른다"였고,
Qwen2.5-1.5B로 같은 실험을 하려 했다(`run_1p5b.sh`). **8GB 보드에서는 안전하게 학습할 수 없어 중단했다.**

```
1.5B LoRA, fp16      가중치 3.17 GB, 할당기 3.9 GB   →  시스템 가용 메모리 196 ~ 297 MB
배치 2 → 배치 1         위와 동일 (배치가 아니라 가중치 자체가 문제)
```

- 9/23 보드 리셋 때 가용 메모리가 170MB였다. 같은 구역이라 300MB 아래로 내려가면 컨테이너를 멈추는
  감시를 붙였고, 학습 첫 스텝부터 걸렸다
- 4비트로 올려 학습하는 QLoRA를 시도했다. PyPI의 bitsandbytes(0.50.2)는 설치는 되지만 Orin(sm_87)에서
  커널이 돌지 않았다(`named symbol not found`). Jetson용 빌드는 받을 수 있는 곳이 없었다
- 남은 방법은 더 큰 GPU에서 학습하고 어댑터만 가져와 Jetson에서 평가·지연을 재는 것이다.
  `run_1p5b.sh`는 그대로 쓸 수 있다

## 학습 중 보드 리셋 — 원인은 메모리였다

200개 학습이 매번 9스텝 근처에서 강제 종료되거나 보드가 로그 없이 재부팅됐다.

- 처음엔 전원 부족으로 판단했으나 틀렸다. 전류 센서(ina3221 ch1 `VDD_IN`)는 19V가 아니라 **모듈 5V 쪽**이라
  크래시 직전 2616mA는 약 13W다. 번들 어댑터(19V 2.37A, 45W)로 충분하다
- `--memlog`로 스텝별 메모리를 찍자 원인이 보였다. PyTorch 실사용(allocated)은 1.06GB로 일정한데
  **캐싱 할당기가 잡아둔 양(reserved)이 3.5→4.6→5.6GB로 불어났다.** Jetson에는 전용 VRAM이 없어
  reserved가 곧 시스템 RAM이고, 가용 메모리가 170MB까지 떨어지면서 OOM kill 또는 시스템 멈춤(→ 워치독 재부팅)이 났다
- 해결: `--mem-fraction 0.6`(기본값, `torch.cuda.set_per_process_memory_fraction`) +
  `PYTORCH_CUDA_ALLOC_CONF=garbage_collection_threshold:0.6`. reserved가 2.8GB에서 멈추고 39/39 완주.
  실제 필요 메모리(peak 2.16GB)는 그대로다
- 진단 도구: `diag_monitor.sh`(0.2초 간격 온도·전압·전류·GPU 클럭·가용 메모리, append+sync)
