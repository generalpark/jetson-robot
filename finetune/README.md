# 자연어 주행 명령 → 제어 명령 변환 (LoRA 파인튜닝)

Jetson Orin Nano 8GB에서 소형 언어모델을 파인튜닝해, 사람이 말하듯 준 주행 명령을
로봇이 그대로 받아쓸 수 있는 제어 명령(JSON)으로 바꾼다.

```
"5초 동안 앞으로 천천히 가면서 왼쪽으로 틀어"
   ↓
{"linear": 0.15, "angular": 0.24, "duration": 5.0}
```

출력 형식은 ROS2 `geometry_msgs/Twist`의 선속도·각속도를 그대로 따른다.

## 왜 파인튜닝까지 했나

먼저 학습 없이 프롬프트만으로 되는지 확인했다. 같은 시스템 프롬프트를 쓰고,
예시를 주지 않은 경우와 3개 준 경우를 각각 측정했다.

예시를 주자 **형식은 완전히 교정됐지만(스키마 63.3% → 100%) 값 정확도는 거의 그대로였다**
(완전일치 1.3% → 2.0%). 형식은 프롬프트로 잡히지만, "천천히"가 0.15 m/s라는
도메인 고유의 대응은 프롬프트로 전달되지 않는다고 보고 학습으로 넘어갔다.

## 결과

| | JSON 파싱 | 스키마 일치 | 방향(부호) | 값 완전일치 |
|---|---:|---:|---:|---:|
| 형식 지시만 (zero-shot) | 100.0% | 62.7% | 14.0% | 1.3% |
| 예시 3개 (few-shot) | 100.0% | 100.0% | 42.0% | 2.0% |
| **LoRA 학습 후** | **100.0%** | **100.0%** | **86.0%** | **74.7%** |

측정은 테스트 150건, 그리디 디코딩 기준이다.

## 검증 손실이 말해주지 않은 것

학습이 끝났을 때 검증 손실은 0.000027이었다. 숫자만 보면 다 맞히는 모델이다.
그런데 같은 모델의 테스트 완전일치는 74.7%였다.

검증셋이 학습과 같은 어휘로 만들어졌기 때문이다. 테스트셋을 **학습에 나온 표현 75건**과
**학습에 없던 표현 75건**으로 절반씩 나눠 다시 재보니 차이가 분명했다.

| LoRA | 방향(부호) | 값 완전일치 |
|---|---:|---:|
| 학습에 나온 표현 (75건) | 100.0% | **100.0%** |
| 학습에 없던 표현 (75건) | 72.0% | **49.3%** |

**틀린 38건은 전부 학습에 없던 표현이었다.** 학습 어휘 안에서는 한 건도 틀리지 않았다.

### 어떻게 틀렸나

| 입력 | 정답 | 생성 | 무슨 일이 났나 |
|---|---|---|---|
| 앞으로 **살살** 가면서 좌측으로 틀어 | linear 0.15 | 0.3 | 모르는 속도어 → 기본값으로 대체 |
| **뒤쪽으로** 가 | linear −0.3 | angular −0.72 | 모르는 방향어 → 다른 항목으로 흘림 |
| 오른쪽으로 **전속력으로** 돌아 | angular −1.2 | −0.72 | 모르는 강도어 → 중간값 |

로봇에서는 두 번째가 가장 위험하다. 후진 명령이 회전 명령이 되면 값이 조금
어긋나는 것과는 다른 종류의 사고가 된다. 속도를 덜 내는 것은 느려질 뿐이지만,
명령의 종류가 바뀌면 의도하지 않은 방향으로 움직인다.

### 대조군을 다시 만든 이유

처음 만든 테스트셋은 150건 중 146건에 새 어휘가 섞여 있었다. 문장이 방향·속도·
어미 등 여러 자리를 쓰다 보니, 한 자리만 새 어휘여도 전체가 "새 표현"으로 분류됐다.
대조군이 4건뿐이어서 비교가 성립하지 않았고, 두 그룹을 75건씩 맞춰 다시 생성했다.

## 지표를 이렇게 나눈 이유

한 개의 정확도만 보면 무엇이 고쳐졌는지 알 수 없다. 실패가 어느 단계에서
나는지 구분하려고 네 단계로 나눴다.

| 지표 | 보는 것 |
|---|---|
| JSON 파싱 | 출력이 JSON이기는 한가 |
| 스키마 일치 | 필요한 키 3개가 모두 있고 숫자인가 |
| 방향(부호) | 앞뒤·좌우를 반대로 보내지 않는가 |
| 값 완전일치 | 속도·시간까지 맞는가 (허용 오차 0.02) |

로봇에서는 **부호가 틀리는 것이 값이 조금 틀리는 것보다 위험하다.**
속도가 0.3이어야 하는데 0.25인 것은 느리게 갈 뿐이지만, 부호가 뒤집히면
반대로 간다. 그래서 부호를 따로 뒀다.

## 어휘를 넓히면 나아지는가 (실험)

일반화가 안 되는 원인이 학습 어휘가 좁아서인지 확인했다.
**데이터 양은 800건으로 고정하고 어휘만 넓혔다**(고유 토큰 33 → 47).
양을 함께 늘리면 무엇이 효과를 냈는지 분리할 수 없다. 테스트셋도 그대로 뒀다.

| 학습에 없던 표현 75건 | 방향(부호) | 값 완전일치 |
|---|---:|---:|
| 기본 어휘 | 72.0% | 49.3% |
| 어휘 확장 | **78.7%** | **49.3%** |

방향은 6.7%p 올랐고 값 정확도는 변하지 않았다. 고쳐진 7건은 전부 방향 오류였고,
그 중 다수는 방향만 바로잡힌 채 값은 여전히 틀렸다.

| 입력 | 기본 | 확장 | 정답 |
|---|---|---|---|
| 우측으로 천천히 돌아 | angular +0.36 | **−0.36** | −0.36 |
| 앞쪽으로 살살 가봐 | angular 0.36 | linear **0.3** | linear 0.15 |

값이 틀린 38건에 들어 있던 새 단어는 `살살`(15), `뒤쪽으로`(14), `전속력으로`(11) 순이었다.
속도어가 남았다.

| 종류 | 어휘 확장 효과 | 이유 |
|---|---|---|
| 방향 (우측으로, 꺾어) | 개선 | `우`·`왼` 등 형태 단서가 있고 문장 내 위치로 유추된다 |
| 속도 등급 (살살, 전속력으로) | 없음 | 형태로 유추할 수 없고 단어의 뜻을 알아야 값이 정해진다 |

**여러 개 중 하나를 고르는 문제는 데이터 다양성으로 개선되지만, 단어를 수치로
옮기는 문제는 개선되지 않았다.** 후자는 데이터를 더 모으는 대신 사전 정규화나,
모르는 단어를 만났을 때 지어내지 않고 되묻는 장치가 맞다고 본다. 로봇에서는
틀린 값으로 움직이는 것보다 멈추고 확인하는 편이 낫다.

재현:

```bash
./run_rich.sh
```

## 데이터

합성 데이터 1,050건(학습 800 / 검증 100 / 테스트 150)을 규칙으로 생성했다.

테스트셋에는 **학습에 한 번도 나오지 않은 표현**을 섞었다(`살살`, `전속력으로`,
`좌측으로`, `앞쪽으로` 등). 학습 어휘로만 평가하면 외운 것인지 규칙을 익힌 것인지
구분할 수 없기 때문이다.

## 8GB에서 돌리기

전체 파라미터 학습은 메모리에 들어가지 않아 LoRA로 어댑터만 학습했다.

- 학습 대상 **8,798,208 / 502,830,976 = 1.75%**
- fp16, gradient checkpointing, batch 4 × 누적 4
- 손실은 정답 JSON 구간에만 건다. 프롬프트까지 학습하면 모델이 질문을 따라 쓴다

## 실행

```bash
python3 gen_data.py --out .          # 데이터 생성
./run_eval.sh zeroshot fewshot       # 학습 전 기준선
./run_train.sh                       # LoRA 학습
./run_eval.sh lora                   # 학습 후 측정
```

## 구성

| 파일 | 내용 |
|---|---|
| `gen_data.py` | 데이터 생성. 학습/테스트 어휘 분리 |
| `train_lora.py` | LoRA 학습. 프롬프트 구간 손실 제외 |
| `evaluate.py` | 4단계 지표 측정. zero-shot/few-shot/LoRA 공통 |
| `analyze.py` | 아는 표현 / 모르는 표현을 나눠 비교 |
| `run_eval.sh`, `run_train.sh` | 컨테이너 실행 |
| `run_rich.sh` | 어휘 확장 실험 (생성 → 학습 → 평가) |
